# 技术选型与实现决策（01–04 落地依据）

本文件回答任务单里悬而未决的四个问题，并记录实现时对任务单的必要偏离。所有结论都基于当前 DSH Desktop **0.2.1-rc.3** 的实际代码核实，不依赖文档记忆。

## 一、SQLite：用 Node 内置 `node:sqlite`

| 方案 | 结论 |
|------|------|
| `node:sqlite`（内置） | **采用**。Node 22.22 与 DSH 运行时 Node 24.21 均实测可用，零依赖、无原生编译、无需登记第三方许可 |
| `better-sqlite3` | 不采用。原生模块编译 + 版本跟随 Electron ABI，装机成本高 |
| 纯 Markdown / JSONL | 作为兜底。运行时若 `node:sqlite` 不可用，自动降级为 append-only JSONL，接口不变 |

实现要点：

- 主库 `data/memory/memory.db`，WAL 模式，`memories` / `audit_log` / `meta` 三表；
- 内容字段（content/summary/tags/tier/importance）写入后**不可 UPDATE**，只允许追加新记录；
- 生命周期字段（access_count / last_accessed / strength / pinned / archived）可更新，每次更新写一条 `audit_log`；
- 删除一律是 `archived = 1`，物理行永不删除。

## 二、LLM 调用：做成可注入，默认走确定性规则

`dailyReview()` 需要「把情景沉淀成特质」。当前没有稳定、公开、可核实的「插件内直接调模型」接口，硬猜字段会踩 `AGENTS.md` 第 5 条红线。

因此：

- `dailyReview({ summarizer })` 接受一个可选的 `async (episodes) => traits` 注入点；
- 未注入时使用内置的确定性归纳器（按标签频次、情绪词、人物出现频次归纳兴趣/偏好/亲密度），完全可单测；
- 将来接入模型只需传入 `summarizer`，不改存储与接口。

## 三、人格注入：走 `ctx.systemPrompt`，不改 pre-step 消息

核实结论：DSH 的系统提示词是一个**每步重新组装的注册表**（`ctx.systemPrompt`），官方支持三种贡献：

| 贡献 | 用途 | 我们用它做什么 |
|------|------|----------------|
| `section({ name, order, text })` | 稳定文本，参与系统提示词组装，KV cache 友好 | 核心人格锚点 + 成长特质 |
| `context({ name, order, text })` | 易变运行时事实，每步重新求值，渲染为带来源的 user 快照 | 记忆摘要（锚点/特质/最近经历） |
| `variable(name, provider)` | `{{name}}` 插值 | 暂不使用 |

任务单 01 写的 `injectIntoPreStep(ctx)` 在 `agent/pre-step` 里改写 messages，这条路**不采用**，原因：

1. 官方注册表就是为「每步重新组装」设计的，改写 messages 会和投影层（surfaceManager / 历史折叠）打架；
2. 直接改 messages 会破坏系统节点稳定性，导致 KV cache 全量失效；
3. 官方 `dsh-persona` 明确「部署级人设归 system-prompt 配置」，插件应在注册表里贡献，而不是劫持瀑布。

`injectIntoPreStep(ctx)` 保留为兼容别名：它注册 section/context，并额外挂一个只观察、`await next()` 原样返回的 pre-step 监听器，用于日志与验收「不阻断 Agent」。

## 四、GUI：宿主 HTTP 路由 + 手写客户端 bundle

核实结论：

- 第三方插件要出现在「设置」导航里，正确插槽是 **`settings.section`**（由基础包 `dsh-client-ui-settings` 声明），配套 `settings.section.icon` 用同一个 `id` 注册图标；「插件市场」（dshmarket）就是这么做的，`order` 决定它在导航里的位置；
- 任务单里写的 `settings.plugin.item` 在当前 **0.2.1-rc.3 不存在**；`plugins.item` 虽然存在，但它是「插件」页里 **「内置插件配置」** 这个列表（官方内置配置页专用，见 plugin-manager README），第三方插件放进去语义不对，且依赖插件管理器内部实现，版本升级有消失风险；
- 客户端 bundle 格式是 `window.__ModuleLoader__.load({ id, factory: (require) => {...} })`，可用平台模块 `react` / `react-dom` / `react/jsx-runtime`，**不需要构建工具**，手写即可；
- 宿主数据通道：第三方插件（如 dshmarket）的既成做法是 `ctx.webServer.register({ kind: 'exact', path, handler })` 注册自有前缀的 HTTP 路由，客户端用 `new URL(path, document.baseURI)` 访问。

因此 04 的实现是：

- 宿主半：`src/gui/api.js` 在 `/fish-dandan/api/*` 下注册只读查询与受控写入，全部经过与模块层同一套校验和安全闸门；
- 客户端半：`src/client/client.js` 手写 loader bundle，注册 `settings.section`（id `fish-dandan`，与「插件」「插件市场」同级）+ `settings.section.icon`，用 `--dsw-alias-*` 语义 token 适配浅色/深色；
- 不新开端口、不直连文件系统、不硬编码密钥；路由只接受回环连接。

> 修正记录：最初把面板注册到 `plugins.item`，结果出现在「插件 → 内置插件配置」下面，属于官方内置配置页的位置。已改为 `settings.section` 独立分区。若以后想让它出现在「插件」页某个包的详情页里，需要以**包**的形式安装并注册 `plugins.bundle.config`（`key` = 包名，插件管理器据此把 `configured` 置真）；当前以绝对路径挂载的开发方式没有包级详情页，用 `settings.section` 更稳。

### DSH 设置分区只保留入口

早期版本在 DSH 面板里做了一套四层折叠表单（人格 / 记忆 / 状态 / 审计），后来删掉了，只留一张入口卡片。原因有三条：

1. DSH 设置区的可用宽度有限，字段一多就必然拥挤，长文本、滑块、审计列表都没有舒展空间；
2. 两套界面同时能写，容易「表单改了一半、网页又改了一半」，用户无法判断哪边是最终值；
3. 校验、审计、就地错误提示在网页里只需实现一次，DSH 面板再实现一遍就是重复维护。

现在这一节只显示：鱼标、名字、运行状态摘要（人格名 · 当前状态 · 记忆条数）、当前状态徽章，以及**唯一的**「打开设置页」按钮。状态是只读的，面板里不存在任何输入控件。

所有设置内容都在网页版，见第五节。

## 五、网页版设置页与平台基座

### 5.1 为什么另做一个网页版

DSH 设置面板只有 800×800，人格这种“字段多、要反复试”的配置在里面很挤。网页版是同一套 API 的另一种界面：

- 宿主直接读 `src/gui/web/index.html`，挂在 `/fish-dandan/ui`，不新开端口；
- 页面是手写的单文件 HTML/CSS/JS，不引外部字体、CDN 与构建工具，离线可用；
- API 基址由宿主在返回 HTML 时注入（`__API_BASE__`），不写死；
- DSH 面板顶部提供「在网页中打开」，链接由 `/overview` 的 `uiUrl` 给出（`webServer.getOrigin() + uiPath`）。

交互上刻意做了三件事，避免“参数太多不敢动”：

1. **只先露两组**：身份、说话方式默认展开；性格五维、偏好、来历、语言习惯都折叠，标题行给出一句话摘要；
2. **右侧实时预览**：每次输入 220ms 防抖后调用 `/persona/preview`，显示“模型每步真正看到的人格段”，改一个字就能看到后果；
3. **显式保存**：只有改动后才出现保存条，未改动时没有按钮；支持 Ctrl/Cmd+S，取消可整体回滚。

### 5.2 平台基座（05）

05 只做契约，不做具体平台：

- `defineAdapter(impl)`：适配器必须实现 `connect / disconnect / normalize / send / capabilities`；
- `routeIncoming(platform, event)`：归一化 → 身份归一 → 写记忆；
- `routeOutgoing(conv, message, { approved })`：总开关 → 人工确认 → 每分钟限流 → 拟人化延迟 → 发送 → 写记忆；
- `resolveIdentity / mergeIdentity / linkIdentity`：`platform + platformUserId ↔ unifiedPersonId`，持久化到 `data/identity/identities.json`；
- `attach(ctx)`：`ctx.effect` 管连接与断开，卸载无残留。

未注册适配器时，`/platforms` 显示“基座已就绪、尚无适配器”，待确认动作会明确返回“要等 06/07 适配器”，不假装执行。

## 六、安全闸门的位置

`src/utils/safety.js` 是唯一入口，被记忆写入、人格写入、GUI 写入共同调用：

1. **注入检测**：命中「忽略以上指令 / ignore previous instructions / 你现在是 / developer mode」等模式 → 记录打 `quarantined` 标记，默认不参与检索与注入，GUI 可见但标红；
2. **密钥脱敏**：`sk-*`、`Bearer *`、`api_key=`、`password=` 等在落库前替换为 `[已脱敏]`；
3. **长度与结构**：单条记忆 ≤ 2000 字，字段类型与枚举严格校验，超限截断并记审计。

安全规则正文独立存放于 `src/utils/safety-rules.md`，人格字段 `safety.safetyRulesRef` 指向它，不与人设文本混写。

## 七、已知取舍

- **记忆召回不做语义向量**：默认 CJK bigram + 词频打分，接口预留 `memoryEmbedding`；不把「能否启动」绑在外部 Embedding 服务上。
- **对外动作不自动执行**：状态机只产出计划并落记忆，`autoExternal` 默认 `false`，任何对外行为都需要人工确认。
- **调度默认开启但只改内部状态**：一个可清理的 `setTimeout` 链，静默时段、每日预算、抖动、最小空闲全部生效；错过只跑最新一次，不重放。

## 九、尚未落地（不影响 01–05 验收）

- 向量检索 `memoryEmbedding` 只留了注入位，尚未实现；
- `dailyReview` 的模型归纳器待接（当前是确定性规则）；
- 05 只做平台基座：QQ / 抖音 / B站分别在 06 / 07 / 08，尚未实现；状态机的 `explore / social / create` 行为目前只产出计划、记忆与待确认项。
- 同类项目里还有两项没吸收：Agent 主动召回工具（需要 DSH 工具契约稳定）、图记忆（构图成本高）。理由见 [同类项目调研与借鉴](./同类项目调研与借鉴.md) 第六节。
- **按对话关闭人设**：现在两段内容注册在全局作用域，所以每个会话都带人格。`systemPrompt` 的 `section.text` 与 `context` provider 都能拿到 `context.scope`，技术上可以按 agent 判断是否注入；但 DSH 的「工作对话」与「陪伴对话」目前没有明确区分依据（同一套 agent preset），需要先确定用目录、preset 还是会话标签来判定，再实现开关。
