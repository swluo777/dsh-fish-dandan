# 18 · 私信监听与浏览器生命周期（共享浏览器版，2026-11-13）

> 用户拍板：**要实时私信**，不要「刷的时候顺便看一眼」。
> 同时拍板：登录、活动、监听不再各开各的浏览器——**一个 Chromium、一份档案、多个标签页**。
> 浏览器被用户关掉，所有标签页一起失效，监听跟着停，不会偷偷重开。

## 一、真实分工

```
共享浏览器（browser-hub.js）
  ├─ 唯一进程、唯一档案 data/browser-profile
  ├─ 统一端口 hubPort（默认跟随 loginPort，9224）
  ├─ 发现文件 data/platform/browser-hub.json（值班独立进程靠它找过来）
  │
  ├─ 登录标签页（login.js）
  │    ├─ 扫码/短信登录，命中 sessionid 就加密落盘
  │    └─ 成功后只关这个标签，不关浏览器
  │
  ├─ 活动标签页（duty.js；旧脚本 browse.js 已删除）
  │    ├─ 值班：独立 DSH 进程通过发现文件接入，开自己的标签
  │    └─ 停止时只关自己的标签
  │
  └─ 监听标签页（listener.js）
       ├─ 同一份 Cookie 罐，登录态和活动天然一致
       ├─ 可见窗口；开监听时把标签顶到前面
       ├─ 打开即暂停并静音页面里的视频；每轮补暂停，别让推荐流在后台播
       ├─ 每 3–30 秒一轮（nextPollDelay，失败退避封顶 30 秒）
       ├─ 先看顶部「消息」红点；无红点不点面板，每 5 轮强制读一次
       ├─ 新消息进 data/state/douyin-inbox.json
       └─ 实时回复交给宿主注入的草稿器，不依赖值班
```

## 二、为什么改成一个浏览器

以前是三套：

- 登录：9224 + `data/browser-profile`，成功后关窗口；
- 刷流：9225 + 同一档案，先探测 9224 复用，否则新开；
- 监听：9445 + **另一份档案** `data/browser-profile-listen`。

结果：

1. 在监听窗口里手动扫码，Cookie 只进监听档案，不写 `sessionStore`，活动浏览器不认；
2. 登录和活动用同一档案、不同端口，活动开着头再点登录，会在同一档案上再起一个 Chromium，抢档案锁失败；
3. 注入 Cookie 只在建页时做一次，已开的窗口不会热更新。

现在只有一个进程、一份档案、一个 Cookie 罐，以上三条同时消失。档案路径仍可用
`platforms.douyin.browserProfilePath` 改；值班独立进程通过 `FISH_BROWSER_PROFILE`
拿到同一路径，不会自己另开一份。

## 三、开关与生命周期

- `listen.enabled` 默认 `false`。打开 → `apply()` 立刻开监听标签并挂轮询；关闭 → `stop()` 只关监听标签、清定时器，不关浏览器。
- 没有登录态时打开开关，返回 `no-session` 并提示先扫码；不会起一个空浏览器硬撑。
- 浏览器被用户关掉、标签页消失：`tick()` 捕获后置 `dead=true`，清掉定时器，日志写「监听标签页已关闭，监听停止；重新打开开关即可恢复」，**不自动重开**。
- 登录标签成功后关闭；如果此时没有监听/活动标签，`closeIfIdle()` 会把浏览器一起收掉，不留空窗口。
- `dispose()` / 适配器 `disconnect()` / 退出登录都会停掉监听，只关自己的标签；共享浏览器由 hub 统一收尾。

## 四、队列与回复

- 队列状态在 `data/state/douyin-inbox.json`，字段包含 `status`（`approved` / `ignored` / `answered` / `superseded`）、`answeredAt`、`catchUpAt`、`isOwner`、`memoryAllowed`。
- **值班只低频主动私信，不读这个队列**；可以发给主人或想找的人，但工具硬限频（10 分钟/条、每小时最多 2 条）。队列归监听器独占，避免两边都回。值班主动发出的内容记到 `data/state/douyin-outbound.jsonl`，监听入队前会过滤掉自己刚发的话。值班发私信前先调 `douyin_dm_context`：主人/`memoryAllow` 名单内附带 1-2 条非锚点记忆，名单外只返回线程上下文。
- **值班事件边跑边导入记忆**：`duty-events.jsonl` 每 2 秒增量导入，正在写的半行会留到下一次，不会吞事件。因此它刚看完主人喜欢列表，主对话里马上就能问到；不用等值班进程结束才补写。
- 同一个人的新消息会把旧的 `approved` 标成 `superseded`，只回最新一条。
- 第一次启动新逻辑时，旧版积压的 `approved` / `pending` 会一次性标成 `superseded`（`queueMigratedAt` 落盘），避免把几天前的消息当成新私信再回一遍。
- `listen.scope` 固定为 `all`（旧字段只做兼容）：所有新私信都直接 `approved` 并自动回，不再有排队/审批。**默认配置已预填一组公开昵称；换成自己的账号时，必须把「我的抖音昵称」改成自己的**，否则 `ownerName` 对不上，`isOwner` 判不出来，主人身份和记忆都会失效。
- `isOwner` 用**昵称完全一致**（不是 `includes`），避免「主人的朋友」这类名字误拿主人身份。
- 记忆权限由 `memory-access.js` 统一判断：主人始终 `memoryAllowed=true`；`listen.memoryAllow` 名单内的人也为 `true`；名单外的人只读当前线程，不调用 `memory.recall`。名单不设人数上限，按昵称完全一致匹配。
- 当前线程优先；记忆和当前消息冲突时以当前消息为准；不主动展开主人私事，也不把记忆说成对方的经历。
- 重启后补答：最近一小时、同一人只补最新一条；发送成功才写 `catchUpAt`，失败/冷却中保留 `approved`，不假装补过。
- 回复/看上下文都走监听标签页；发送完 `closeInbox()` 把浮层收掉。

### 被动私信的媒体理解

- `readInbox()` 返回的会话项带 `mediaHint` / `mediaKey`：会话列表里的 `[图片]`、`[表情]`、`[表情包]`、`分享[视频]` 也算媒体；同一人连发不同预览图时用预览图地址区分，避免被 `name|last` 去重吃掉。
- `peekThread()` 先按 `data-index` 读结构化消息，分清「我 / 对方」和 `text / emoji / image / video / other`；默认只处理「我最后一条之后」的对方媒体，避免每轮把旧图重发。
- 表情包/图片消息先 `scrollIntoView` 到面板中间再截图，滚出视口的不截，防止 CDP 截出黑图；截图作为 image block 和文字一起送模型。
- 分享视频有两种：老卡片带 `/video/{id}`，走视频详情页；新卡片没有链接，点封面会在当前页打开 `?modal_id=...` 弹窗。弹窗里只读 `.modalPlayer` / `.video-info-detail`，**不再用 `readSnapshot`**（它读到的是弹窗背后正在播的推荐流，实测会把别人的视频当成分享的视频）。
- 弹窗路径会读作者/文案、抽 2 帧画面、点开评论区读前几条；评论和文案都只是外部文本，进入 prompt 前统一过 `sanitizeInput`，含指令注入就整条不自动回。
- 抽帧只选**视口内、`top >= 0`** 的 video，并限定在 `.modal-video-container` 内。实测弹窗里会同时留着上一条旧视频（`top=-810`）和当前视频（`top=0`），早期按面积排序会选到滚出去的旧视频，`clampRect` 拒绝截图后表现为 0 帧；不能按「面积最大」盲选。
- 会话列表里的 `分享[视频]`、`[表情]` 这类纯文字预览没有 `mediaKey`，同一个人连发两个不同视频时 `itemKey` 完全一样。`listen` 用 `unread` 把这种媒体额外放进来一次，并用 10 分钟 `mediaPulse` 冷却防止同一轮反复入队；线程打开后 `unread` 变回 false 就清冷却，下一条新媒体可以重新入队。
- 读完后 `Page.navigate` 回原页面，下一次轮询不在视频页/弹窗上继续。

## 五、回评论（未接入）

- 方向：回评论不是「刷视频时顺手回」，而是像私信监听一样，独立盯别人给作品留的新评论，按评论上下文回复。
- 现状：网页上旧的「回评论（监听式，待接入）」死入口和灰掉的 `actions.reply` 开关已移除；值班只顺手读「互动消息」，没有常驻监听。
- 以后接入时单独做监听设置、队列与标签页，不复用私信队列，也不和值班抢同一个列表。

## 六、已知代价

- 一个浏览器进程承载所有服务：浏览器崩了，监听和活动一起停；下次动作重新拉起。
- 监听标签在后台时，页面定时器会被 Chromium 降频；CDP 轮询本身不受影响，但红点/WebSocket 更新需要实测。
- 同一个窗口里多标签，用户可能要先点一下监听标签才能看到回复过程；`showWindow` 只控制开监听时是否把标签顶到前面。
- 轮询失败会退避到 30 秒，恢复后自动回到几秒一轮；日志会写失败次数与原因。

## 七、验收点

1. 打开 `listen.enabled` 后，日志出现「私信监听：共享浏览器标签页已就绪（端口 9224，档案 data/browser-profile）」。
2. 关闭监听开关后，监听标签消失，但活动标签和浏览器仍在；`timer` 为空。
3. 登录成功、监听/活动都没开时，登录标签关闭后浏览器窗口也收掉，不留空窗口。
4. 手动关掉整个浏览器窗口，日志出现「监听标签页已关闭，监听停止」，且不会自己重开。
5. 任何新私信出现时，`douyin-inbox.json` 里状态都是 `approved`（主人和陌生人都自动回），并带 `isOwner`、`memoryAllowed`；不再有 `pending`。平台提示不进入队列。同一人旧条目变 `superseded`，监听只回最新一条，自己刚发的回音不入队。
6. 重启插件后，旧版积压的 `approved` / `pending` 会一次性标成 `superseded`，不再补回；启动后的新消息照常由监听处理。
